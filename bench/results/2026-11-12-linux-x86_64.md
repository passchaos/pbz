# pbz cross-language benchmark snapshot (2026-11-12, Linux x86_64)

This snapshot is the repository-verifiable evidence for the current
functionality/performance audit in `bench/COVERAGE.md`.

## Environment

- CPU: 13th Gen Intel(R) Core(TM) i9-13900K (32 hardware threads)
- OS: Ubuntu 24.04.5 LTS, Linux 6.x, x86_64
- Zig: 0.16.0
- Rust: rustc/cargo 1.101.0-nightly
- Go: 1.22.2
- C++: GCC 13.3.0, protobuf 35.1 (conformance-pinned build) and system
  protobuf 3.21.12 for rows that 35.1 intentionally rejects
- All benchmark commands were pinned to CPU 3 with `taskset -c 3` and
  `GOMAXPROCS=1`. The machine was shared with other builds, so small
  differences below ~5% are not significant; the harness reports the best of
  three samples.

## Commands

```sh
PBZ_COMPARE_CPUSET=3 PBZ_COMPARE_LATEST_CPP=1 bench/run_compare.sh 2>&1 | tee /tmp/pbz-compare.log
python3 bench/summarize_compare.py /tmp/pbz-compare.log --fail-on-loss
python3 bench/summarize_compare.py /tmp/pbz-compare.log --pivot --exclude-zero-copy > fair.md
```

`PBZ_COMPARE_LATEST_CPP=1` builds the full C++ benchmark against protobuf 35.1
from the same source archive used by the upstream conformance suite. The
summarizer keeps the last row for duplicate names, so 35.1 numbers override the
system 3.21.12 rows; the older rows remain only for workloads 35.1 rejects
(for example a leading plus sign in Duration JSON).

## Post-hardening spot check

The generated-code conformance hardening changed error sets and default-skip
conditions but not the benchmark hot paths. A spot check against the final code
on the same machine measured TextBytes `decode owned reuse` at 81 ns (table:
77.36 ns) and Complex `decode owned reuse` at 290 ns (table: 286.94 ns), both
within run-to-run noise.

## Copy-path follow-up (2026-11-13)

The destination-alignment prefix in `pbz.wire.copyBytes` was replaced with one
overlapping 32-byte store instead of up to four scalar 8-byte stores. Same-run
copy probes improved 1 KiB off=3 copies from 11 ns to 8 ns, 4 KiB from 34 ns to
31 ns, and 8 KiB from 69 ns to 63 ns. The packed bool encode probe dropped from
14 ns to 11 ns.

Same-session focused comparison against the protobuf 35.1 C++ baseline (both
pinned to the same CPU, load ~28):

| row | pbz | C++ 35.1 | pbz / C++ |
|---|---:|---:|---:|
| packed bool encode | 10 ns | 11.82 ns | 1.18x |
| packed fixed32 encode | 36 ns | 39.36 ns | 1.09x |
| largebytes encode | 2532 ns | 2659 ns | 1.05x |
| packed fixed64 encode | 67 ns | 62.59 ns | 0.93x |

The remaining fixed64/sfixed64/double encode difference is memory-bound: glibc's
AVX memcpy copies the 8 KiB payload in ~60 ns while pbz's vector loop needs
~62-63 ns.

## 2026-11-13 re-run (loaded machine)

`PBZ_COMPARE_CPUSET=3 PBZ_COMPARE_LATEST_CPP=1 bench/run_compare.sh` was re-run
after the copy-path change while the machine was heavily loaded (load average
30-45). Mixed mode stayed clean (`All parsed cross-language rows are pbz wins.`).
Fair-mode deltas were dominated by contention: generated fixed64 and sfixed64
packed encode share the same copy path yet measured 61.7 ns and 80.3 ns in that
run, and packed decode rows showed similar row-to-row swings. The same-session
focused probes above are the reliable signal. Treat the 2026-11-12 snapshot as
the reference table and re-run the fair gate on an idle machine before drawing
sub-10% conclusions.

## Remaining fair-mode gaps (2026-11-12 run)

- `packed sfixed64 encode`: pbz 62.92 ns vs C++ 62.62 ns (0.5%).
- `packed double encode`: pbz 62.18 ns vs C++ 62.03 ns (0.2%).
- `packed bool encode`: pbz 14.18 ns vs C++ 11.42 ns (24%, 2.8 ns absolute).

The two 64-bit packed encode rows are inside the run-to-run noise observed on
this shared machine. A same-session probe of the packed bool encode row measured
C++ at 11.48 ns, pbz's generated encode at 14 ns, its manual tag+length+copy path
at 12 ns, and a bare 1 KiB copy at the same destination offset at 12 ns. The
residual ~2.5 ns is the 1 KiB copy implementation: glibc's AVX memcpy measures
~7.5 ns for the same copy while pbz's compiler_rt/vector copy measures
~10-11 ns. Generated-code bookkeeping is not the cause, and the 4 KB/8 KB copy
rows are already at parity or faster.

Mixed mode has no residual gaps.
