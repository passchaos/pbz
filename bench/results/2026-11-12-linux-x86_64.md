# pbz cross-language benchmark snapshot (2026-11-12, Linux x86_64)

This snapshot is the repository-verifiable evidence for the current
functionality/performance audit in `bench/COVERAGE.md`.

## Environment

- CPU: 13th Gen Intel(R) Core(TM) i9-13900K (32 hardware threads)
- OS: Ubuntu 24.04.5 LTS, Linux 6.x, x86_64
- Zig: 0.16.0
- Rust: rustc/cargo 1.101.0-nightly
- Go: 1.22.2
- C++: GCC 13.3.0, protobuf 35.1 (conformance-pinned build) and system
  protobuf 3.21.12 for rows that 35.1 intentionally rejects
- All benchmark commands were pinned to CPU 3 with `taskset -c 3` and
  `GOMAXPROCS=1`. The machine was shared with other builds, so small
  differences below ~5% are not significant; the harness reports the best of
  three samples.

## Commands

```sh
PBZ_COMPARE_CPUSET=3 PBZ_COMPARE_LATEST_CPP=1 bench/run_compare.sh 2>&1 | tee /tmp/pbz-compare.log
python3 bench/summarize_compare.py /tmp/pbz-compare.log --fail-on-loss
python3 bench/summarize_compare.py /tmp/pbz-compare.log --pivot --exclude-zero-copy > fair.md
```

`PBZ_COMPARE_LATEST_CPP=1` builds the full C++ benchmark against protobuf 35.1
from the same source archive used by the upstream conformance suite. The
summarizer keeps the last row for duplicate names, so 35.1 numbers override the
system 3.21.12 rows; the older rows remain only for workloads 35.1 rejects
(for example a leading plus sign in Duration JSON).

## Copy-path follow-up (2026-11-13)

The destination-alignment prefix in `pbz.wire.copyBytes` was replaced with one
overlapping 32-byte store instead of up to four scalar 8-byte stores. Same-run
copy probes improved 1 KiB off=3 copies from 11 ns to 8 ns, 4 KiB from 34 ns to
31 ns, and 8 KiB from 69 ns to 63 ns. The packed bool encode probe dropped from
14 ns to 11 ns.

## Lean JSON value tree (2026-11-13)

The upb baseline exposed pbz's only consistent cross-language gap: JSON parse
was 1.5-2.3x slower than upb because every generated and dynamic parse first
built a `std.json.Value` DOM (`StringArrayHashMap` per object, one allocation
per key/string) and then walked it to fill the message.

`src/json_value.zig` now provides a protobuf-specific `Value` tree with the
same tag/API surface used by generated code (`.object`, `.array`, `.string`,
`.integer`, `.float`, `.number_string`, `object.iterator()/get()/count()`,
`array.items`). The parser is a strict RFC 8259 recursive-descent parser with:

- string/key slices borrowed from the input text (generated `jsonParse` makes
  one arena-owned copy of the input, so returned messages stay self-contained);
- duplicate-key rejection with linear checks for small objects and a lazy hash
  set after 16 entries (protobuf conformance requires `DuplicateField`);
- a 512-level depth limit and full escape/surrogate/UTF-8 validation;
- one arena release for the whole DOM in the dynamic path.

## Generated duplicate-field tracking (2026-11-13)

Generated JSON fill previously rejected exact duplicate object keys through the
DOM parser but accepted the same field reached through two accepted spellings
(`{"big_delta":1,"bigDelta":2}`) and accepted two different members of one
oneof. The dynamic path already rejected both. Generated fill now keeps a
comptime `std.StaticBitSet` of field indices and oneof indices and returns
`error.DuplicateField` on either case, including `null` values. Extension
duplicate keys remain last-wins (documented residual).

## Generated well-known-type JSON (2026-11-13)

Generated fields typed as a well-known type previously used the generic
message JSON path: a `google.protobuf.Timestamp` field expected
`{"seconds":...}` instead of the canonical `"2020-01-02T03:04:05.123Z"` string.
A probe with generated `Timestamp`, `Duration`, `Int32Value`, repeated
`Timestamp`, oneof `Timestamp`, `FieldMask`, and `Empty` fields now round-trips:

```text
at=1577934245 count=7 mask0=foo_bar mask1=baz.qux empty_set=true
json: {"at":"2020-01-02T03:04:05.123Z","count":7,"mask":"fooBar,baz.qux","empty":{}}
```

All nine wrapper types were checked in one message: `DoubleValue` NaN,
`FloatValue` 1.5, quoted `Int64Value`/`UInt64Value` extremes, signed/unsigned
32-bit values, `BoolValue false`, `StringValue` with an escaped quote, and
`BytesValue` base64. A wrapper set to JSON `null` is unset and omitted from
output. `FieldMask` converts lowerCamelCase JSON paths to snake_case storage and
back; `Empty` accepts only `{}`. `src/wkt.zig` gained `jsonParseUnquoted`
variants for Timestamp, Duration, and FieldMask so generated code parses the
lean value tree without re-serializing it.

Residual: generated `Any`/`Struct`/`Value`/`ListValue` JSON still goes through
the dynamic path. `src/codegen.zig` includes a unit test that generates code for
all supported WKT field shapes and checks the emitted parse/stringify
expressions. `zig build test` and `zig build check` pass.

## Generated JSON conformance audit (2026-11-13)

`PBZ_CONFORMANCE_GENERATED_JSON=1` makes the generated conformance driver parse
JSON requests with the generated message parsers and emit JSON output with the
generated stringifier, instead of bridging through the dynamic path. This is an
opt-in audit mode; the default driver still passes 2808/445 through the dynamic
bridge.

Audit progression as generated JSON support was filled in:

| state | successes | failures | remaining failure classes |
|---|---:|---:|---|
| initial generated JSON audit | 2734 | 74 | Any, Struct/Value/ListValue, URL-safe base64, null oneof, float overflow |
| after base64 + null-oneof fixes | 2742 | 66 | Any, Struct/Value/ListValue |
| after Struct/Value/ListValue | 2762 | 46 | Any, wrapper output, float overflow, null Value |
| after output/presence fixes | 2786 | 22 | Any only |

The audit drove these fixes:

- generated base64 now calls `pbz.json.decodeBase64`, which accepts standard
  and URL-safe alphabets, padded or unpadded, and ignores non-canonical trailing
  bits like the reference parsers;
- JSON `null` for a oneof member is ignored instead of clearing a previously
  set member, while `null` for `google.protobuf.Value` and `NullValue` members
  sets the null value as required;
- generated `jsonFloat` rejects numeric overflow to infinity;
- generated `jsonStringifyWithOptions` uses an explicit `anyerror` set so
  mutually recursive messages compile when stringify is instantiated;
- `Struct`/`Value`/`ListValue` fields use recursive generated converters that
  map arbitrary JSON objects/arrays/scalars onto the generated message tree;
- a present-but-empty raw message field is emitted as `{}` instead of being
  skipped, and `NullValue` enum output is `null`;
- generated `Value` number output rejects NaN/Infinity.

All 22 remaining failures are `Any` JSON tests (11 cases x Protobuf/JSON
output). Generated `Any` JSON needs type-URL resolution across same-file and
imported messages; the dynamic path already handles it, and generated
`jsonParseConformant` remains the full-coverage entry point.
